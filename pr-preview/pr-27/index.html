  • Receipts

    A query engine in Rust, compiled to WebAssembly, that lets you click any number computed from NYC 311 data and see the rows behind it.

    to load and verify 7.1M rows in the browser
    1.2–1.35 s
    to trace a number back to 443,530 rows
    ≤ 15 ms
    to re-derive a result without one row (2.5 s re-run)
    63 ms

    How it works

    • Runs over content-addressed Arrow IPC snapshots in 64Ki-row chunks. The browser re-derives every BLAKE3 hash on load and refuses data that doesn’t match.
    • Captures lineage at every operator (selection vectors, CSR group membership) for backward and forward tracing, adding about 6% to execution time on 7.1M rows.
    • Computes exact counterfactuals: it re-derives a result without chosen rows, recomputing only the affected groups when it can, and matches a full re-run bit for bit.
    • Nine workspace crates, 100 Rust tests including property tests, a pyarrow differential oracle, and a check that the WASM build’s output equals the native engine’s byte for byte.

    Architecture

    1. Socrata API 143 pages of 50,000 records, 3.1 GB of JSON
    2. Snapshot CLI clean, dedupe, sort; BLAKE3 over 64Ki-row chunks
    3. Arrow IPC + manifest LZ4 buffers, 239 MB, named by its hash
    4. Verify on load WASM re-derives every hash before use browser
    5. Plan a validated, hashed DAG, described in plain English browser
    6. Operators + lineage selection vectors, CSR group membership browser
    7. Trace and what-if rows behind a number; the number without them browser
    Hard parts
    Data the page can prove it didn’t alter
    The engine trusts nothing it is handed. A dependency-free Arrow IPC reader, bounds-checked on every read, decodes the file and re-derives the manifest, chunk, dictionary and column hashes and the sort order row ids depend on. A flipped byte or a truncated download is refused with a sentence saying what didn’t match.
    Counterfactuals that are exact, not estimated
    Removing rows before a single aggregate only changes their groups, so only those are recomputed, and the result is compared bit for bit with a full re-run. Cost follows the size of the affected group, not the table: one Bronx row out of 443,530 takes 63 ms where a re-run takes 2.5 s.
    The same answer on one thread or four
    Parallel code only splits work whose result doesn’t depend on order (hashing, decoding, filtering, stable sort). Aggregation stays sequential so decimal sums round the same way, and the property tests run with and without the parallel feature.

    Code

    A percentile without each row, for every row at once. Leave-one-out over a sorted group: removing a value shifts the rank by at most one place, so 443,530 exact answers take one pass. 

    /// The `p`th percentile without each member, given the non-null
/// `(value, position)` pairs in the executor's order. Removing a value
/// shifts the rank by one place at most, and it always picks a value, so
/// the result is exact.
fn percentile_without(sorted: &[(CfValue, usize)], n: usize, p: u8) -> Vec<CfValue> {
    let all = percentile_rank(sorted.len(), p).map_or(CfValue::Null, |r| sorted[r].0);
    let mut out = vec![all; n];
    let rest = sorted.len().saturating_sub(1);
    for (rank, (_, pos)) in sorted.iter().enumerate() {
        out[*pos] = percentile_rank(rest, p).map_or(CfValue::Null, |r| {
            sorted[if r < rank { r } else { r + 1 }].0
        });
    }
    out
}

  • Chapter – a reading app

    An offline-first RSVP speed reader for EPUB, PDF, and text files, installable as a PWA.

    to index all 216,820 words of Moby-Dick
    147 ms
    per search, typos and prefixes included
    ≈ 1 ms
    transferred on a first visit; offline after that
    278 KB

    How it works

    • Parses EPUBs with JSZip and DOMParser (OPF manifest and spine) and PDFs with pdf.js in Web Workers, reading pages in parallel on multi-core machines and stripping running headers.
    • Times each word against performance.now() deadlines so playback doesn’t drift, weighting length, punctuation, rare words, and first mentions of names, then normalizing so the chosen WPM is the true average.
    • Full-text search runs in a Web Worker over an Int32Array inverted index, with stemming, prefix matching, and an edit-distance fallback for typos.
    • Books, progress, and bookmarks persist in IndexedDB. CI runs more than 200 Vitest unit tests and the Playwright suite on desktop and phone, plus a checker for the interface’s own rules.

    Architecture

    1. EPUB, PDF, TXT, MD JSZip + DOMParser; pdf.js in up to two workers
    2. Parse worker words, paragraphs, chapters, pictures worker
    3. IndexedDB books by content hash, progress, bookmarks
    4. Search worker inverted index, names, pacing extras worker
    5. Timeline a Float32Array of weights that averages to your WPM
    6. Playback clock each word due at an absolute time
    7. Word or page view pinned focus letter, or a pacer over real pages
    Hard parts
    A rhythm that doesn’t drift
    Chained timers add their lateness to every word. Each word is instead scheduled against the time it was due, so a late timer shortens the next wait rather than pushing the whole book back, and a tab that falls a second behind resyncs instead of racing to catch up.
    The speed you set is the speed you get
    Long words, punctuation, rare words and a character’s first appearance all get extra time. The weights are then normalized across the book, so 300 wpm is the true average and the time-left estimates stay accurate.
    Search that stays instant on a long book
    Indexing runs in a worker when a book opens, into typed arrays: sorted term ids for binary-search prefix matching and one Int32Array of positions per term. A misspelt word falls back to the closest term by bounded edit distance.
    An interface with rules that are tested
    The design rules (tokens only, 44px targets, sheets that close three ways, nothing wider than a 320px screen) are checked by a script over the source and a Playwright suite over the running app, so a regression fails CI rather than waiting to be noticed on a phone.

  • stems

    An infinite jukebox: it finds the moments in a song that match and plays it forever, splicing between them where you can’t hear the seam.

    faster FFT in WASM SIMD than in JavaScript
    3.4–3.8×
    to analyse a 5-minute track
    2.8 s
    page heap with stems, using shared memory
    394 → 24 MB

    How it works

    • All the DSP is written from scratch in TypeScript: STFT, mel and chroma features, onset detection, a dynamic-programming beat tracker, self-similarity and phrase structure. The FFT is also AssemblyScript compiled to WASM SIMD.
    • Every jump is bar-aligned, scored over four beats of context on each side, then aligned to the exact sample by cross-correlation, with a crossfade chosen from that correlation that never splits a drum hit.
    • Playback runs in an AudioWorklet over SharedArrayBuffer PCM and starts as soon as the file is decoded; analysis and stem separation run in workers and hand over mid-block.
    • Separates drums, bass, vocals and other with a built-in DSP separator, or with HTDemucs through onnxruntime-web on WebGPU or WASM. Nothing leaves the device.

    Architecture

    1. Audio file decoded to PCM in a SharedArrayBuffer
    2. AudioWorklet plays at once, straight through, until seams arrive audio thread
    3. Analysis worker STFT → onsets → tempo → beats → features worker
    4. Beat graph beat distances, meter, phrases, jump edges worker
    5. Planner Tarjan SCC keeps playback out of dead ends
    6. Seam builder align, adaptive fade, varispeed, loudness
    7. Splicer per stem each stem gets its own crossfade law audio thread
    Hard parts
    Seams you can’t hear
    Beat times are only good to about 10 ms, which is audible. At each jump a small range of lags is searched for the offset where the incoming audio best matches the outgoing audio, so bass waveforms and transients line up in phase; the same correlation picks a constant-gain or equal-power fade.
    Music that can never run out
    Beats and jump edges form a graph. Playback is kept inside its largest strongly connected component, found with an iterative Tarjan, where every beat can reach every other, so there is no dead end near the end of the song.
    Keeping the main thread out of the audio path
    Jumps are planned well ahead inside the worklet, so a throttled background tab doesn’t interrupt the music. Sharing PCM instead of copying cut the stall when stems arrive from 564 ms to 132 ms. A service worker adds the COOP and COEP headers GitHub Pages can’t send.

    Code

    Lining a seam up to the sample. Normalised cross-correlation between the outgoing and incoming audio. The lag that maximises it is where the jump lands. 

    function ncc(a: Float32Array, aOff: number, b: Float32Array, bOff: number, len: number): number {
  let ab = 0, aa = 0, bb = 0;
  for (let i = 0; i < len; i++) {
    const ai = aOff + i, bi = bOff + i;
    const x = ai >= 0 && ai < a.length ? a[ai] : 0;
    const y = bi >= 0 && bi < b.length ? b[bi] : 0;
    ab += x * y; aa += x * x; bb += y * y;
  }
  const den = Math.sqrt(aa * bb);
  return den > 1e-12 ? ab / den : 0;
}

  • Music Generation

    A PyTorch melody model that continues a musical prompt, with a demo that runs the trained Transformer in your browser.

    parameters, shipped as 1.6 MB of float16
    810,240
    per token for the JavaScript forward pass
    ≈ 1.5 ms
    notes in key once sampling is key-constrained
    0.79 → 1.00

    How it works

    • A decoder-only Transformer with rotary position embeddings, pre-LayerNorm, and a sliding-window KV cache, compared against token and piano-roll LSTM baselines.
    • A REMI-style event tokenizer with tempo-aware quantization. Sampling supports temperature, top-k, and nucleus sampling, a grammar mask, and key constraints estimated with Krumhansl–Schmuckler.
    • The demo reimplements the forward pass in JavaScript over 1.6 MB of float16 weights in a Web Worker, parity-tested against the PyTorch logits.
    • Trained with AdamW, warm-up and cosine decay, and early stopping, and evaluated with perplexity and Yang & Lerch musical metrics. The pytest suite runs on Python 3.10–3.12 in CI.

    Architecture

    1. MIDI files loaded with repair for bad meta events
    2. Beat-grid quantizer 16th-note steps at any tempo; skyline melody
    3. REMI tokens bar, position, velocity, pitch, duration; 148 in all
    4. Transformer 4 layers, 4 heads, d = 128, RoPE, KV cache
    5. Constrained sampling grammar and key masks, then top-p
    6. Web export float16 weights + held-out prompts
    7. Browser the same forward pass in a Web Worker browser
    Hard parts
    Two implementations that must agree
    The browser demo is a second forward pass, written by hand in JavaScript. A pytest module runs it under Node and checks it against PyTorch: logits from the same weights with and without the sliding cache, token encodings and grammar masks along random walks, filtered probabilities and the musical metrics.
    Output that is always valid music
    The token grammar is regular (position, velocity, pitch, duration; positions rise within a bar), so the set of legal next tokens is computed at every step and sampling is masked to it. Key, register and monophony go through the same mask, with no retraining.
    Rebuilding a notebook that looked like it worked
    The original coursework notebook had fifteen faults, documented one by one: frames per second mistaken for steps per beat, validation windows overlapping training windows by 47 of 48 frames, a softmax over independent note probabilities. Each has a fix and a test.

    Code

    Attention over the cache, by hand. One head of causal self-attention in plain JavaScript: scores against every cached key, a stable softmax, then a weighted sum of cached values. 

    const scale = 1 / Math.sqrt(hd);
const scores = state.scores;
for (let hIdx = 0; hIdx < H; hIdx++) {
  const o = hIdx * hd;
  let max = -Infinity;
  for (let j = 0; j < n; j++) {
    let s = 0;
    const base = j * d + o;
    for (let i = 0; i < hd; i++) s += q[o + i] * ks[base + i];
    scores[j] = s * scale;
    if (scores[j] > max) max = scores[j];
  }
  let sum = 0;
  for (let j = 0; j < n; j++) { scores[j] = Math.exp(scores[j] - max); sum += scores[j]; }
  this.att.fill(0, o, o + hd);
  for (let j = 0; j < n; j++) {
    const wj = scores[j] / sum, base = j * d + o;
    for (let i = 0; i < hd; i++) this.att[o + i] += wj * vs[base + i];
  }
}

  • Does Morality Pop Out?

    An EEG replication of Gantman et al. (2020) with 34 participants, published as an interactive page that refits the statistics in the browser.

    of EEG data, with nothing the model needs lost
    1.5 GB → 2.3 MB
    to refit a model as you drag a time window

    How it works

    • Found a bug in the original analysis: R’s gee() only clusters contiguous rows, so the published models fit about 5,000 one-trial clusters instead of 34 participants. Fixing it changes one conclusion.
    • Ported the gee package’s exchangeable-correlation GEE with sandwich variance to JavaScript, matching 66 reference fits from R to about 1e-12.
    • Compressed 1.5 GB of EEG data into 2.3 MB of per-participant moments in 25 ms bins, so any time window can be refit in about 0.35 ms.
    • Includes a one-minute version of the masked word task with requestAnimationFrame timing. The full report is written in Quarto and R.

    Architecture

    1. Raw recordings eeg.csv, 1.5 GB, on OSF
    2. Moment builder Python: counts, sums, cross products per 25 ms bin
    3. eeg.json 2.3 MB of per-participant moments
    4. GEE in JavaScript a port of the gee package’s ugee.c browser
    5. SVG charts hand-written; refit on every drag browser
    6. R reference fits 66 models from the real package, checked in tests tests
    Hard parts
    A published analysis that clustered nothing
    gee() treats rows as one cluster only when they sit next to each other. The original code sorted by trial, so each row came from a different participant than the one before, and the “robust” errors were plain HC0 errors from trial-level OLS. The published numbers match that fit to every printed digit. Sorting by subject moves one effect from p = .027 to p = .057.
    Refitting 1.5 GB in a browser tab
    With one 0/1 predictor, the estimator only needs each participant’s count, sum and sum of squares per condition, plus cross products between time bins for an arbitrary window. Storing those instead of trials makes any window refit in a third of a millisecond.
    Matching R, not approximating it
    The port follows the C source: the same start from the glm fit, the same moment estimates for scale and correlation, the same stopping rule, then the sandwich variance. It agrees to about twelve digits on the analysis windows and seven on binned ones, where the moments are stored as 32-bit floats.

    Code

  • Brightness Perception

    A jsPsych experiment, run on Prolific, testing whether a word’s emotional valence biases how bright a gray square looks.

    the most a 400 ms word can miss its target by
    ½ frame
    simulated studies per run of the power figure
    1,000
    CDN scripts pinned and hash-verified in CI
    7 of 7

    How it works

    • A custom jsPsych plugin sequences fixation, word, and probe with requestAnimationFrame, logging measured display durations and reaction times on the performance clock.
    • Seeded, reproducible randomization of 80 trials, with a repeat-detection cover task, an accuracy-gated practice block, and a valence-rating manipulation check.
    • Analysis runs in the browser and in Node: response rates by valence and cover-task d′ with the Hautus log-linear correction. Results export as CSV.
    • CI verifies the subresource-integrity hashes of CDN scripts, then runs node:test unit tests and Playwright end-to-end tests.

    Architecture

    1. Config + word lists every timing, grey level and key in one file
    2. Design seeded order, six repeats, a break halfway
    3. Word-probe plugin cross → word → square, on animation frames
    4. Data rows answers plus measured durations per trial
    5. Analysis rates by valence; d′ for the cover task
    6. Debrief + CSV exported in the browser; nothing uploaded
    Hard parts
    Honest timing on an unknown display
    A 400 ms word can only last a whole number of frames. The plugin measures the frame interval as it runs and switches on the frame where less than half a frame of the target is left, then saves the measured durations on every row, so a dropped frame is visible in the data instead of silently lengthening the prime.
    Two answers from one trial
    In the original design, pressing Space for a repeated word replaced the brightness judgement. Here the repeat key is listened for from word onset to the end of the trial, separately, so the cover task never costs a data point.
    A power analysis you can check by eye
    The project page simulates 1,000 studies in the browser, tests each with a one-sample t test built on the regularized incomplete beta function, and plots them beside an analytic curve. The two agree within a few points.

    How it works

    • Recording and export are separate. On Windows, a native engine grabs frames with DXGI desktop duplication, keeps only the 32×32 tiles that changed, and writes them LZ4-compressed; elsewhere ffmpeg records, and the same exporter takes over.
    • GIFs come from a built-in encoder: an exact palette when a clip uses 255 colours or fewer (median cut otherwise), an LZW coder, and frames that store only the rectangle that changed. MP4 uses Windows’ own H.264 encoder.
    • Zooms are planned like an editor would cut them: nearby clicks share one view, the camera holds still between them and moves on a critically damped spring, and no zoom hides a click.
    • The pointer is sampled at about 120 Hz and drawn at export as a smoothed, anti-aliased arrow, with optional click rings. For scripts and agents there is --json output, bv stop and a Claude skill. About 100 tests, no network access.

    Architecture

    1. Capture DXGI duplication or GDI; ffmpeg on macOS and Linux
    2. Changed tiles 32×32 tiles, a whole band skipped in one compare
    3. .bvraw + pointer track LZ4 frames; position and buttons at 120 Hz
    4. Zoom planner shots planned from the whole take’s clicks export
    5. Renderer crop and scale, drawn pointer, rings, frame export
    6. Encoders built-in GIF; H.264 or VP9 for video export
    Hard parts
    A camera that is already there when you click
    Zoom is applied at export, when the whole recording is known. Clicks less than 3 s apart that fit one view share a zoom, the camera is fully in half a second before the first click, and two zooms are never closer than 1.5 s, so the clip doesn’t yo-yo.
    Recording that costs almost nothing when the screen is still
    Frames are compared in the capture buffer, a band of tiles at a time; an unchanged band is settled by one comparison, and only changed tiles are copied and compressed. The exporter then re-renders only the rows under changed pixels.
    A pointer drawn after the fact
    The pointer isn’t in the captured frames. Its path is smoothed with a spring, pulled back onto the recorded path around each click so it is exactly where you clicked, and drawn as a signed-distance arrow through the zoom. A still pointer leaves frames identical, which keeps GIFs small.
    A command line an agent can drive
    With --json, stdout is exactly one line; exit codes separate errors, bad arguments and cancelled takes; bv stop ends a background recording and waits for the export. Recording this page’s clips found one gap, a region past the screen edge failing with ffmpeg’s bare “Invalid argument”, which is now caught up front.

    Code

    Keeping only the tiles that changed. The inner loop of the raw recorder: an unchanged band of tiles is skipped with one comparison, and a changed tile is copied into both the record and the reference frame. 

    for i in 0..tile_count(w, h) {
    let (x, y, tw, th) = tile_rect(i, w, h);
    // A band of tiles is a contiguous run of rows: when it hasn't
    // changed at all (most of a typical screen), one comparison
    // settles every tile in it.
    if !first && x == 0 {
        let band = y * w * 4..(y + th) * w * 4;
        if bgra[band.clone()] == self.prev[band] {
            // Skip to the next band's first tile.
            skip_to = i + cols;
        }
    }
    if i < skip_to {
        continue;
    }
    let rows = (y..y + th).map(|r| (r * w + x) * 4..(r * w + x + tw) * 4);
    let changed = first
        || rows
            .clone()
            .any(|span| bgra[span.clone()] != self.prev[span]);
    if changed {
        self.payload.extend_from_slice(&(i as u32).to_le_bytes());
        for span in rows {
            self.payload.extend_from_slice(&bgra[span.clone()]);
            if !first {
                self.prev[span.clone()].copy_from_slice(&bgra[span]);
            }
        }
    }
}
